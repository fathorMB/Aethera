# M-13 — Release automatica su GitHub: installatore Windows da un tag

## Outcome

Un push di un tag v* sul repository produce, senza passi a mano sulla macchina dell'operatore, una GitHub Release in bozza con l'installatore NSIS di Aethera, il suo SHA-256 e le note prese da RELEASE-NOTES.md; ogni pull request passa gli stessi controlli (build del frontend, vitest, cargo test); una versione diversa fra tag, tauri.conf.json e Cargo.toml ferma la release. L'installatore scaricato dalla release è quello che l'operatore installa e prova. La firma digitale resta fuori.

## Tasks

- [x] T-01 Workflow di release (.github/workflows/release.yml): su push di un tag v*, runner windows-latest, Rust e Node con cache, npm ci, tauri build, GitHub Release in bozza con l'installatore NSIS, il file .sha256 e il testo della versione preso da RELEASE-NOTES.md; nessun segreto oltre GITHUB_TOKEN
- [x] T-02 Controllo della versione nel workflow: il tag, tauri.conf.json, Cargo.toml e il titolo della finestra devono dire la stessa versione, altrimenti la release si ferma con un messaggio che dice quale file correggere
- [x] T-03 Workflow dei controlli (.github/workflows/ci.yml) su pull request e push su main: build del frontend, vitest, cargo test e cargo clippy senza errori; niente esempi E2E che hanno bisogno del motore, della GPU o di C:\AetheraData
- [!] T-04 Prova del workflow su un tag di prova (per esempio v0.1.0-rc.1) con release in bozza: durata, uso della cache e dimensione dell'installatore annotati; release di prova e tag cancellati solo dopo il via dell'operatore — Serve il via dell'operatore ai push. Sequenza: (1) git push -u origin m13-release-workflow, poi merge su main (il workflow di tag usa i file del commit taggato, quindi il tag va messo su un commit che contiene .github/); (2) git tag -a v0.1.0-rc.1 -m "Aethera 0.1.0-rc.1, prova del workflow" <commit su main> && git push origin v0.1.0-rc.1; (3) gh run list --workflow release.yml -L 1, poi gh run watch <id> --exit-status; (4) gh release view v0.1.0-rc.1 (bozza, pre-release, due asset .exe e .exe.sha256, note), annotare durata dei job, cache (log di rust-cache) e dimensione dell'installatore; (5) solo dopo il via: gh release delete v0.1.0-rc.1 --yes --cleanup-tag e git tag -d v0.1.0-rc.1
- [x] T-05 Documentazione: sezione del README su come si fa una release (versione nei tre posti, note, tag, pubblicazione della bozza) e nota nelle RELEASE-NOTES che l'installatore non è firmato e che cosa mostra Windows SmartScreen
- [ ] T-06 [operatore] Scaricare l'installatore dalla release di prova, verificarne lo SHA-256 e installarlo; se c'è una VM pulita, farlo lì, e la stessa prova chiude la clausola «senza Rust né Node» di M-07 T-02
- [ ] T-07 [operatore] Via al tag v0.1.0 vero e pubblicazione della release in bozza, dopo le prove aperte di M-05, M-06 e M-07 (M-07 T-07)

## Notes


**Da dove viene.** Richiesta dell'operatore il 16-09 sera: una release con installatore pubblicata da un workflow GitHub. M-07 produce l'installatore solo in locale (T-01) e aspetta il tag (T-07); `.github/workflows` non esiste e sul repository non c'è ancora nessuna release.

**Vincoli.**
- La firma digitale resta fuori (scelta dell'operatore): l'installatore resta non firmato e lo si dice nelle note.
- `fathorMB/Aethera` è privato: i minuti dei runner Windows costano il doppio di quelli Linux. Serve la cache di Rust e Node, e i controlli girano su Windows solo dove servono.
- Ogni push, compresi i tag di prova, si chiede all'operatore prima (vedi memoria «Push e pubblicato»). Una release in bozza non è pubblicata: la pubblicazione è dell'operatore.
- La coda con le modifiche di M-12 (branch `m12-finestra-v2`) non si tocca: il workflow si scrive su main.

**Fuori dal milestone.** Firma del codice, aggiornamento automatico dell'app (updater di Tauri), build per macOS e Linux, pubblicazione su winget.
